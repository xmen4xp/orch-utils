# Extension REST API — Design Specification

## 1. Problem Statement

The Nexus API Gateway currently only exposes REST endpoints derived from the Nexus datamodel graph (CRD-based routes). There is no mechanism to expose **custom REST API endpoints** that are not part of the datamodel but need to be proxied through the same gateway — for example, telemetry query APIs backed by a separate microservice.

Teams need the ability to:

- Declare custom REST API paths in the datamodel DSL
- Have the Nexus compiler generate Kubernetes CRs from those declarations
- Have the API Gateway dynamically register and proxy those routes to a backend service
- Detect and reject route collisions between extension APIs and datamodel-generated routes
- Include extension API paths in the auto-generated OpenAPI specification

## 2. Design Overview

The solution introduces two new Kubernetes Custom Resources and a corresponding DSL type:

| Component | Purpose |
|-----------|---------|
| `nexus.ExtensionRestAPI` (DSL) | Go struct in the datamodel declaring a custom API path |
| `ExtensionRestAPI` (CRD) | Kubernetes CR generated by the compiler; describes URI, methods, OpenAPI spec |
| `ExtensionRestAPIEndpoint` (CRD) | Kubernetes CR (deployed at runtime); provides backend service + port |
| Compiler parser + generator | Parses DSL, validates, and renders CR YAML |
| API Gateway controllers | Reconcile CRs, register routes, proxy requests |
| Route Registry | Singleton in-memory registry for collision detection |

### Request flow

```
Client → API Gateway (Echo) → Route Lookup → Extension Handler → HTTP Proxy → Backend Service
```

1. A request arrives at the API Gateway.
2. The unified handler checks if the URI+method matches an extension route (via in-memory cache keyed by `METHOD:URI`).
3. If matched, the extension handler resolves the backend endpoint from the `ExtensionRestAPIEndpoint` cache.
4. The request is proxied to the backend service with original headers, body, query params, and an added `X-Nexus-Hierarchy` header containing resolved parent label context.
5. The backend response is returned verbatim to the client.

## 3. DSL Definition

Extension REST APIs are declared as Go variables of type `nexus.ExtensionRestAPI` in the datamodel package:

```go
type ExtensionRestAPI struct {
    Uri             string       `json:"uri"`
    Methods         []HTTPMethod `json:"methods,omitempty"`
    OpenAPIPathSpec string       `json:"openAPIPathSpec,omitempty"`
}
```

### Example usage in a datamodel

```go
package config

import (
    "net/http"
    "github.com/.../nexus/nexus"
)

// nexus-extension-rest-api:config.Config
var ProjectMetricsAPI = nexus.ExtensionRestAPI{
    Uri:     "/v1/projects/{projects.Project}/metrics",
    Methods: []nexus.HTTPMethod{http.MethodGet},
    OpenAPIPathSpec: `
get:
  tags:
    - Metrics
  summary: Get project metrics
  parameters:
    - name: start
      in: query
      required: true
      schema:
        type: string
        format: date-time
  responses:
    "200":
      description: Metrics data
    "400":
      description: Bad request
`,
}
```

**Key conventions:**

- The `// nexus-extension-rest-api:<pkg>.<Type>` annotation associates the API with a Nexus graph node. This determines:
  - The parent hierarchy (used for the `X-Nexus-Hierarchy` header)
  - Path parameter validation (params must reference valid nodes in the hierarchy)
  - OpenAPI grouping (tagged by associated node type)
- `Methods` restricts which HTTP methods are proxied. If empty, defaults to `GET`, `PUT`, `PATCH`, `DELETE`.
- `POST` is **not** a supported method — Nexus owns object creation semantics.
- `OpenAPIPathSpec` is optional raw YAML merged into the auto-generated OpenAPI spec.

## 4. Compiler Changes

### Parser

The parser:

1. Scans all packages for variables of type `nexus.ExtensionRestAPI`
2. Extracts `Uri`, `Methods`, `OpenAPIPathSpec` from the AST
3. Resolves the associated node from the `// nexus-extension-rest-api` comment annotation
4. Validates:
   - URI is non-empty
   - Path parameters reference valid nodes in the associated node's hierarchy
   - `OpenAPIPathSpec` (if provided) is valid YAML with at least one supported HTTP method
   - Supported methods: `GET`, `PUT`, `PATCH`, `DELETE`

### Generator

Generates one `ExtensionRestAPI` CR YAML per DSL variable:

- **CR name**: `<package>-<lowercased-variable-name>` (e.g., `config-projectmetricsapi`)
- **Nexus annotation**: JSON annotation with hierarchy and associated node metadata
- **OpenAPI spec**: Embedded in the CR spec for the API Gateway to serve

### Template

```yaml
---
# Generated by nexus. DO NOT EDIT.
apiVersion: nexus.com/v1
kind: ExtensionRestAPI
metadata:
  name: {{.Name}}
  annotations:
    nexus: |
      {{.NexusAnnotation}}
spec:
  uri: {{.Uri}}
  methods: {{.Methods}}
  openAPIPathSpec: |
    {{.OpenAPIPathSpec}}
```

## 5. Kubernetes Custom Resource Definitions

### ExtensionRestAPI

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: extensionrestapis.nexus.com
spec:
  group: nexus.com
  scope: Cluster
  names:
    kind: ExtensionRestAPI
    plural: extensionrestapis
    singular: extensionrestapi
    shortNames: [erapi]
  versions:
    - name: v1
      served: true
      storage: true
      subresources:
        status: {}
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: [uri]
              properties:
                uri:
                  type: string
                methods:
                  type: array
                  items:
                    type: string
                    enum: ["GET", "PUT", "PATCH", "DELETE"]
                openAPIPathSpec:
                  type: string
            status:
              type: object
              properties:
                phase:
                  type: string
                  enum: ["Registered", "Rejected", "Pending"]
                message:
                  type: string
                registeredRoutes:
                  type: array
                  items:
                    type: object
                    properties:
                      uri: { type: string }
                      method: { type: string }
                collisions:
                  type: array
                  items:
                    type: object
                    properties:
                      uri: { type: string }
                      method: { type: string }
                      conflictingCR: { type: string }
                      conflictingSource:
                        type: string
                        enum: ["nexus-crd", "extension-rest-api"]
                lastUpdated:
                  type: string
                  format: date-time
```

### ExtensionRestAPIEndpoint

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: extensionrestapiendpoints.nexus.com
spec:
  group: nexus.com
  scope: Cluster
  names:
    kind: ExtensionRestAPIEndpoint
    plural: extensionrestapiendpoints
    singular: extensionrestapiendpoint
    shortNames: [erapiendpoint]
  versions:
    - name: v1
      served: true
      storage: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: [extensionRestAPIRef, service, port]
              properties:
                extensionRestAPIRef:
                  type: string
                  description: Name of the ExtensionRestAPI CR this endpoint serves
                service:
                  type: string
                  description: Fully qualified service DNS name
                port:
                  type: string
                  description: Service port number or name
```

**Relationship**: An `ExtensionRestAPIEndpoint` references an `ExtensionRestAPI` by name via `spec.extensionRestAPIRef`. This separation allows the datamodel (compiler-generated) to define _what_ endpoints exist, while deployment configuration (service + port) is provided separately at runtime.

## 6. API Gateway Components

### 6.1 Route Registry

A singleton route registry tracks all registered `URI + Method` combinations across both Nexus CRD routes and extension routes.

- **Data structure**: Maps a normalized URI to a map of HTTP methods to route owners
- **Route owner**: Contains the source type (nexus-crd or extension-rest-api), CR name, and GVR
- **URI normalization**: Converts Echo-style `:param` to template-style `{param}` for consistent comparison
- **Collision semantics**: First-come-first-served. Re-registration by the same owner is idempotent.

Key operations:

| Operation | Description |
|-----------|-------------|
| Register | Register a route with URI, method, and owner; returns error on collision |
| Unregister | Remove a single route by URI and method |
| Unregister by CR | Remove all routes owned by a specific CR |
| Check collision | Pre-check for collisions without modifying state |

### 6.2 In-Memory Cache

Two caches maintain extension state:

1. **Extension API spec cache** — keyed by composite `"METHOD:URI"`
   - Enables O(1) lookup during request handling
   - Updated on CR create/update/delete
   - On delete: iterates all entries, removes those matching the CR name

2. **Extension endpoint cache** — keyed by ExtensionRestAPI CR name
   - Provides backend service resolution
   - Updated when ExtensionRestAPIEndpoint CRs are reconciled

Channel notifications signal the Echo server to register/unregister routes when cache state changes.

### 6.3 Reconcilers

#### ExtensionRestAPI Reconciler

On create/update:
1. Fetch the CR via dynamic client
2. Parse spec (URI, methods, OpenAPI path spec, nexus annotation)
3. Determine methods (explicit or default: GET, PUT, PATCH, DELETE)
4. **Check for collisions** against the route registry
5. If collision detected → update CR status to `Rejected` with collision details; do **not** register routes
6. If no collision → register routes in the route registry, update CR status to `Registered`, update in-memory cache

On delete:
1. Unregister all routes for this CR from the route registry
2. Remove all cache entries for this CR

#### ExtensionRestAPIEndpoint Reconciler

On create/update:
1. Fetch the CR via dynamic client
2. Parse spec (extensionRestAPIRef, service, port)
3. Update the endpoint cache

On delete:
1. Remove the endpoint from cache

**Note**: Endpoint changes do **not** trigger an Echo server restart — they only update the in-memory cache. The next proxied request will use the updated endpoint.

### 6.4 Echo Server Integration

#### Route registration

Extension routes are registered in the Echo server by listening on a channel for new extension API specs. Each extension route is registered as an Echo route matching all HTTP methods, with the unified Nexus handler as the handler function.

#### Route replay on server restart

The CRD reconciler restarts the Echo server whenever datamodel annotations change. This destroys all registered routes. Nexus CRD routes are replayed by the annotation processor, but extension routes must be replayed from the in-memory cache.

During server initialization, all cached extension routes are re-registered to restore state after each restart.

### 6.5 Request Handling

The extension proxy handler:

1. Resolves the backend endpoint from the endpoint cache
2. Builds the backend URL: `http://<service>:<port><resolved-uri>?<query-params>`
3. Substitutes path parameter placeholders with actual values from the request
4. Copies all request headers and body
5. Adds `X-Nexus-Hierarchy` header — a JSON object mapping node names to their resolved values from Kubernetes labels (e.g., `{"config.Config": "default", "projects.Project": "proj1"}`)
6. Proxies the request with a 30-second timeout
7. Returns the backend response verbatim (status code, headers, body)

### 6.6 OpenAPI Integration

Extension API paths are merged into the per-datamodel OpenAPI spec. The OpenAPI path spec YAML from the CR is parsed and converted into OpenAPI path items with:
- Tags derived from the associated node type
- Response codes and descriptions from the YAML
- Query parameters and descriptions from the YAML

## 7. Collision Detection

Collisions are detected at the `(URI, Method)` level:

| Scenario | Result |
|----------|--------|
| Extension CR registers `GET /v1/projects/:id/metrics` | ✅ Registered |
| Another Extension CR registers `GET /v1/projects/:id/metrics` | ❌ Rejected (collision with first CR) |
| Extension CR registers `PUT /v1/projects/:id/metrics` (same URI, different method) | ✅ Registered |
| Nexus CRD already owns `GET /v1/projects/:id` | Extension CR attempting `GET /v1/projects/:id` → ❌ Rejected |
| Extension CR deleted | Routes freed; another CR can register them |

Collision resolution is **first-come-first-served**. The rejected CR's status is updated with details about which CR owns the conflicting route.

## 8. Status Reporting

The `ExtensionRestAPI` CR status subresource provides observability:

```yaml
status:
  phase: Registered          # or "Rejected" or "Pending"
  message: "All routes registered successfully"
  lastUpdated: "2026-05-20T21:30:00Z"
  registeredRoutes:
    - uri: /v1/projects/{projects.Project}/metrics
      method: GET
  collisions: []             # Populated when phase is "Rejected"
```

## 9. Supported HTTP Methods

| Method | Supported | Notes |
|--------|-----------|-------|
| GET | ✅ | |
| PUT | ✅ | |
| PATCH | ✅ | |
| DELETE | ✅ | |
| POST | ❌ | Nexus owns object creation semantics |
| HEAD | ❌ | Not supported for extension APIs |
| OPTIONS | ❌ | Not supported for extension APIs |

When `spec.methods` is omitted, defaults to: `["GET", "PUT", "PATCH", "DELETE"]`.

## 10. Deployment

### Helm chart changes

- The API Gateway Helm chart includes the `ExtensionRestAPI` and `ExtensionRestAPIEndpoint` CRDs.
- Compiler-generated `ExtensionRestAPI` CRs are installed alongside CRD YAMLs during datamodel installation.
- `ExtensionRestAPIEndpoint` CRs are created by the platform team at deployment time, pointing to the actual backend services.

### Example deployment

```yaml
# Deployed by datamodel installer (compiler-generated)
apiVersion: nexus.com/v1
kind: ExtensionRestAPI
metadata:
  name: projects-projectmetricsapi
  annotations:
    nexus: '{"name":"projects.Project","hierarchy":["config.Config"]}'
spec:
  uri: /v1/projects/{projects.Project}/metrics
  methods: ["GET"]
  openAPIPathSpec: |
    get:
      summary: Get project metrics
      responses:
        "200":
          description: Metrics data

---
# Deployed by platform team / Helm values
apiVersion: nexus.com/v1
kind: ExtensionRestAPIEndpoint
metadata:
  name: projects-projectmetricsapi-endpoint
spec:
  extensionRestAPIRef: projects-projectmetricsapi
  service: metrics-api.hdai-system.svc.cluster.local
  port: "8080"
```

## 11. Testing

### E2E test coverage

| Test case | Description |
|-----------|-------------|
| CR generation | Verify compiler-generated `ExtensionRestAPI` CRs exist and have `Registered` status |
| Route collision rejection | Create a second CR with overlapping `(URI, Method)` → verify `Rejected` status with collision details |
| Non-colliding registration | Create a CR with same URI but different method → verify `Registered` status |
| OpenAPI spec | Verify extension paths appear in the datamodel OpenAPI JSON |
| Proxy to backend | Deploy a mock nginx backend, create `ExtensionRestAPIEndpoint`, send GET request through API Gateway → verify proxied response |

## 12. Limitations and Future Work

- **No POST support**: POST is reserved for Nexus-managed object creation.
- **No TLS to backend**: Backend proxy uses plain HTTP. HTTPS support can be added via endpoint spec extension.
- **Single endpoint per API**: Each `ExtensionRestAPI` maps to exactly one `ExtensionRestAPIEndpoint`. Load balancing is expected to be handled by the backend Kubernetes Service.
- **No authentication passthrough configuration**: All request headers are forwarded as-is. Fine-grained auth header management is not yet configurable.
- **In-memory only**: Route registry and caches are in-memory. On API Gateway pod restart, state is rebuilt from CR reconciliation.
